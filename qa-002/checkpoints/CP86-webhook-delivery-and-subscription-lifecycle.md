# CP86 — Webhook event integration and subscription lifecycle

- **Baseline:** frozen RC4 `40bba5b55c2da6fc00b107b315c9b3167fb20169`; no Tanpopo implementation changes.
- **Runtime/browser:** isolated SQLite Tanpopo `127.0.0.1:18084`; authenticated Operator + Org Owner; real Chromium, 1440×900.
- **Result:** subscription registration and synthetic kill-switch event persistence PASS for this slice. Live outbound delivery BLOCKED by managed Cloud direct egress. Subscription revocation FAIL, new finding DEF-034. Existing DEF-020 recurred.

## Actions and results

1. Opened Operations → Webhooks in the real Console. It showed zero subscriptions and required a public HTTPS URL plus a write-only `WEBHOOK_HMAC_SECRET`. In Providers → Vault Secrets, left the existing Google credential untouched and sealed a fresh 32-byte synthetic HMAC credential. The UI showed only the fingerprint and confirmed plaintext could not be read again. The actual credential submission and post-seal screens were visually inspected.
2. Created a temporary receiver token at the public `webhook.site` service. The token and full endpoint URL stayed in mode-0600 `/tmp` files and were never printed or added to repository evidence. The receiver defaulted to no-content success. Registered the receiver from Operations → Webhooks for only `kill_switch.triggered`; Tanpopo returned HTTP 201. The rendered table showed `https://webhook.site`, the subscribed event and Enabled state. The full receiver path did not appear in the screenshot or application list response.
3. Opened Security → Kill Switches. The real Preview blast-radius control visually displayed **0 organizations · 1 project · 0 virtual keys · 0 connections** for the existing synthetic `QA002 CP78 Fresh Budget` project. With no active switch present, submitted the project freeze with an explicit QA reason and exact project slug through the two-step confirmation. The active record returned HTTP 200, affected one entity, severed zero streams, and persisted audit event sequence 379. This created one synthetic `kill_switch.triggered` event for the selected webhook.
4. Queried the disposable receiver. It observed zero requests. The isolated delivery row reached `DEAD_LETTER` after eight attempts, with no HTTP status and safe error `transport failure`. No raw event body, request headers, signature or external token was retained.
5. Inspected Cloud environment status: observations were current, policy was unrestricted and enforced, and no network diagnostics were returned. A direct no-proxy HTTPS probe failed during DNS resolution (HTTP 000); a managed-shell-proxy HTTPS probe to the same public site returned HTTP 200. Source inspection shows Tanpopo's SSRF-guarded HTTP client intentionally does not use `http.ProxyFromEnvironment`. This provides an environment-specific explanation for direct egress failure. It does not prove Tanpopo webhook delivery is broken on a direct-egress deployment. Delivery and HMAC verification are therefore **BLOCKED / UNVERIFIED**, not a new delivery defect. See [QA-OBS-015](../reports/QA-OBS-015-cloud-egress-blocks-guarded-webhook-delivery.md).
6. Tried to remove the subscription from the actual UI: the list has no Actions column or row action. An authenticated CSRF-protected `DELETE /admin/v1/webhooks/{id}` returned HTTP 404 `resource_not_found`; the route table registers only GET/POST for the collection. Since the product had no removal path, the exact subscription and its one dead-letter row were removed transactionally from the **isolated QA SQLite database only**. The unrelated event outbox and audit history were retained. This is the confirmed Moderate lifecycle/security finding [DEF-034](../reports/DEF-034-webhook-subscription-cannot-be-revoked.md).
7. Cleared the one test-project kill switch through Security → Kill Switches, HTTP 200. API and page state showed zero active switches and the clear event persisted at audit sequence 382. In the same browser session, the global Kill Switch pill and Security navigation badge still displayed `1` after the page showed zero, reproducing existing **DEF-020**. A separate fresh session showed the count reconciled. No new defect ID was added for this recurrence.
8. Deleted both test vault credentials through the real Providers → Vault Secrets UI; both `DELETE /admin/v1/secrets/{id}` operations returned 204. Deleted the external receiver token; the external service returned 204. Read-only database checks confirmed zero rows for the test subscription, delivery and test vault credentials, and zero active switches. The existing Google credential remained untouched. Public QA evidence contains neither secret value nor receiver token.

## Finding, scope and limits

- **DEF-034 Moderate — confirmed:** after registration, there is no Console disable/delete action; authenticated DELETE returns 404. The UI does not allow administrators to revoke a destination. Acceptance criteria are in the report.
- **DEF-020 — recurrence:** stale global/navigation count after a project switch was cleared. The page/API had zero but the same-session badges showed one; a fresh session reconciled.
- **QA-OBS-015 — environment:** managed shell proxy works, but guarded application direct DNS/egress to the synthetic public receiver does not. No product delivery or signature defect is inferred.
- **No new defect:** no evidence of a security boundary bypass, unauthorized access, receiver data leakage, or wrong-tenant delivery. The endpoint remained public and event content synthetic.

**Delivery and signature coverage remains UNVERIFIED** until the same workflow is run in an environment supporting direct guarded public egress. Remote receiver 4xx/5xx, retry recovery, signature calculation against an actual received body, subscription rotation/disable behavior (missing), role boundaries and cross-tenant denial remain open. Existing `GATE-REL-07` remains **BLOCKED**; QA-002 is in progress.
