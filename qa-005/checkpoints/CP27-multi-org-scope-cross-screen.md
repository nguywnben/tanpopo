# CP27 — Multi-organization scope and cross-screen context

**Baseline:** frozen source `737079ddb847d97dbcf832f610ed0048556cb65b`; exact-source compiled Linux amd64 runtime `127.0.0.1:18145`, SQLite; authenticated synthetic Operator/Org Owner in Chromium 1440×1000. No product source or specification changes. `GATE-REL-07` remains **BLOCKED**.

## Organization provisioning and switching

In Operations → Organizations, the operator created synthetic organization `QA005 Secondary Org` (`qa005-secondary`). The UI returned to the refreshed organization table and displayed the new row. Clicking **Switch** changed the workspace picker to `QA005 Secondary Org / No project / No env`; the state remained visible after waiting and navigating to Access & Keys. The authorized operator's organization-scoped `GET /admin/v1/projects` returned HTTP 200 with an empty collection, as expected for this new organization.

Access & Keys → Members & Roles, in the secondary organization's organization-only context, returned HTTP 200 with zero members and rendered “No members found.” FinOps returned HTTP 200 for `/admin/v1/budgets` and `/admin/v1/usage/summary`, displayed zero-valued totals and no budgets. These results match the synthetic tenant's empty persisted state; no cross-tenant records were shown in those scoped views. Chromium screenshots were visually inspected: `CP27-secondary-org-created.png`, `CP27-secondary-org-switch-settled.png`, `CP27-secondary-org-members.png`, and `CP27-secondary-org-finops.png`.

## Refresh and scope persistence

After selecting the secondary organization, navigating to Access & Keys, and hard-refreshing, the picker returned to `QA005 Org / Initial Project / dev`. The refreshed Access & Keys view then displayed eight environment keys from that original scope, including revoked test keys and active synthetic keys; this was the original tenant's persisted state, not data from the secondary organization. The same switch-to-secondary then hard-refresh sequence first reproduced on Operations → Organizations. The after-refresh screenshot `CP27-secondary-org-after-refresh.png` was visually inspected and shows the picker reset while the page was still showing its loading placeholder. A second settled run confirmed the reset on Access & Keys after 1.8 seconds, and the populated original-scope rows were read from the rendered page and matched its environment-filtered API response. See `CP27-access-secondary-org-before-refresh.png` and `CP27-access-after-refresh.png`.

Historical CP15 and CP110 demonstrate project/environment selection surviving refresh, but their criteria/evidence do not establish that an operator-selected organization must survive a browser refresh. Source inspection confirms organization selection is held in ConsoleShell React state and initialization chooses a resolved/session organization; that is a mechanism observation, not an acceptance criterion. Therefore this is recorded as **PG-005**, a multi-organization context persistence/product-contract gap, rather than a confirmed implementation defect. Product Owner should define whether refresh should restore the last selected organization or reset to the session/default organization, and the UI should make that behavior predictable. No scope-boundary or authorization failure was observed in this scenario; it is not evidence of full tenant isolation.
