# CP69 — DEF-075 Virtual Key grace expiry boundary

**Source:** exact frozen RC7 `737079ddb847d97dbcf832f610ed0048556cb65b`; runtime binary SHA-256 `62aba8761eae2733b1e8957b0b09cde45dee4fb2c29fa6eb36294ce29a600fe9`, Linux/amd64; isolated SQLite all-role runtime `127.0.0.1:18145`; Chromium 156; synthetic loopback provider route `qa005-chat-route`. No real provider or paid usage.
**Disposition:** **PARTIAL — lifecycle timing is inconsistent across fresh exact-source runs.** The one-time old/new pair was correlated to stored SHA-256 digests. Its HTTP authorization boundary passed at T+30/T+61, but the first post-deadline persistence read remained dual-valid without a finalization audit event. A later isolated run did finalize automatically at deadline +202 ms. Another run's Console render timed out before browser-state evidence could be saved. Do not close DEF-075.

## Reproduction and evidence

1. Signed in as the synthetic Org Owner, selected `QA005 Org / Initial Project / dev`, and issued an environment-scoped PROVIDER key for the local deterministic route. A pre-rotation bearer canary returned HTTP 200. Independent read-only SQLite checks matched the one-time old key's SHA-256 digest to `active_key_hash` and confirmed the key's project/environment matched the route.
2. Used the real Console Rotate action. A test-only Playwright request interceptor changed the grace field to the documented supported 60-second minimum; Tanpopo source was unchanged. Rotation returned HTTP 200, `ROTATING_DUAL_VALID`, v2. SQLite matched the old digest to `previous_key_hash`, the replacement digest to `active_key_hash`, and recorded the grace deadline.
3. At T+30, both old and replacement bearers returned HTTP 200. At T+61, the old bearer returned HTTP 401 `invalid_virtual_key` and the replacement returned HTTP 200. This confirms the credential authorization boundary remained secure at the tested boundary.
4. Immediately after those requests, the correlated key's independent SQLite read and authenticated Admin API both still returned `ROTATING_DUAL_VALID`, v2, with the grace deadline uncleared. The Admin audit slice contained `virtual_key.rotated` and `virtual_key.created` but no `virtual_key.rotation_finalized`. This reproduces the lifecycle defect on the exact RC7 runtime. The key was then successfully revoked (HTTP 200).
5. A separate fresh UI-correlated run created and rotated another key. The rerun's Console page did not finish rendering within 15 seconds after reload, so its UI result is UNVERIFIED and its HTTP T+30/T+61 outputs were not preserved. Read-only SQLite and audit evidence nevertheless show `virtual_key.rotation_finalized` at 1795748251770 ms, 60.202 seconds after `virtual_key.rotated` at 1795748191568 ms; its row was `CREATED_ACTIVE`, v3, with cleared grace fields. The Owner then revoked that test key (HTTP 200).
6. An earlier fresh run also correlated old and new digests and observed T+30/T+61 authentication outcomes, then returned `CREATED_ACTIVE` v3 with a `virtual_key.rotation_finalized` event. Its inspected Console screenshot showed the key inventory as Active. This successful transition conflicts with step 4 and is preserved in the result evidence rather than omitted.

## Classification and limits

The acceptance contract requires old-key denial and new-key success at expiry, followed by bounded served-runtime cleanup: clear previous-key/grace fields, persist `CREATED_ACTIVE` with an incremented version, refresh Console state, and emit one linked `virtual_key.rotation_finalized` event. The security behavior passed in one well-correlated exact-source run; the persisted lifecycle did not meet that contract in the first post-deadline read, while other runs did finalize. The variable timing/visibility and missing browser result prevent a reliable closure. Keep **PARTIAL** pending repeatable bounded finalization and same-key UI/API/database agreement.

Coverage is one SQLite all-role runtime, one synthetic route, one Owner workflow and a 60-second grace. No held-open streams, concurrent rotation/revocation race, process restart, multi-node, PostgreSQL/Valkey, alternate role, browser/platform matrix, provider credential, or paid call was tested. The prior QA-004 FAIL and earlier QA-005 partial evidence remain preserved.
