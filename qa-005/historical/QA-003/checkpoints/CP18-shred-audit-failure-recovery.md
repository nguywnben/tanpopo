# CP18 — Tenant crypto-shred after audit-storage failure

**Baseline:** RC5 `3423d4f523ef0ac77469a1201b8b753d1d31c902`
**Status:** injected SQLite audit failures and recovery tested on isolated clones; QA-003 remains in progress. `GATE-REL-07` remains **BLOCKED**.

## Reproduction and actual result

1. Created isolated copies of the restored SQLite database on ports 18113 and 18114. Installed a test-only SQLite `BEFORE INSERT` trigger in each copy that aborts only `audit_events` inserts for `organization.crypto_shredded`. No Tanpopo files or product tests were changed.
2. On the populated clone, used Chromium UI to create organization `QA003 CP18 Populated Shred Audit Failure`, project `CP18B Shred Project`, environment `CP18B Shred Environment`, and a provider-plane Virtual Key. The tested organization had one organization DEK, one project DEK, project, environment, and Virtual Key before shred. Evidence: [project](../evidence/CP18B-project-created.png), [environment](../evidence/CP18B-environment-created.png), and [Virtual Key after issuance](../evidence/CP18B-vkey-present.png). The one-time Virtual Key secret was not retained in evidence.
3. From Operations → Organizations, entered the exact slug and confirmed Crypto-shred. The Admin API returned HTTP 500 `failed recording shred audit event`; the UI displayed the same error. Evidence: [sanitized response](../evidence/CP18B-shred-audit-failure-ui.json), [confirmation](../evidence/CP18B-shred-audit-failure-ready.png), and [failure-state UI](../evidence/CP18-shred-audit-failure-result.png). The latter is a second empty-tenant reproduction that clearly shows the error banner; CP18B evidence independently shows the populated tenant and HTTP 500.
4. Read the populated clone’s DB read-only immediately after failure. The organization remained with status `DELETING`; organization and project DEK rows were gone; project, environment, and Virtual Key rows remained; its audit chain had the four create events and no crypto-shred receipt. A durable `vault_shred_requests` row reported `COMPLETED`. In the separate empty-tenant reproduction, a subsequent Console project-create attempt returned `organization is not active`; [screenshot](../evidence/CP18-project-create-blocked-during-deleting.png). This is a useful state-transition signal, but the Organizations list did not label the remaining row as `DELETING` or explain recovery; when selected, it showed `Active` while the project-create error said the organization was not active.
5. Removed only the injected trigger and retried Crypto-shred using the same exact slug. The UI reported success, the organization row disappeared, and one Virtual Key was reported revoked. Read-only post-retry inspection found no organization, DEK, project, environment, Virtual Key, or project-key rows. The retained chain now ended with `organization.crypto_shredded`; authenticated product verification returned HTTP 200, intact, five events. See [retry result](../evidence/CP18B-shred-retry-complete.png) and [audit verification](../evidence/CP18B-shred-audit-chain-result.json). The empty-tenant retry is also captured [here](../evidence/CP18-shred-retry-complete.png).

Sanitized pre-failure population: [CP18B population result](../evidence/CP18B-population-result.json). Consolidated counts and state transitions: [CP18 recovery evidence](../evidence/CP18-shred-failure-recovery-result.json).

## DEF-007 disposition and new finding

- **DEF-007 remains PARTIAL.** CP04 verified transactional rollback for organization/project/environment creation audit failures. CP18 shows the organization teardown is intentionally phased: the erasure fence and DEK destruction occur before the final transaction that removes mutable records and appends the hash-chained receipt. When that final audit append fails, the first irreversible phases remain committed. This is recoverable by retry after the audit sink is healthy, but is not an all-or-nothing transaction across DEK destruction, mutable purge, and receipt. Other mutation types, disk-full/IO failures, other engines, concurrent races, and automated recovery remain unverified.
- **DEF-041 Moderate — confirmed UX/operations defect in an injected audit-outage scenario.** The UI/API reports a generic shred failure although the DEKs have already been irreversibly destroyed, leaves a visible tenant row with child resource records and no audit receipt, and gives no phase-specific state or retry guidance. Retrying after restoring audit writes completed safely. This is a recovery/status contract issue; no data exposure or permanent inability to finish was observed. See [standalone engineering handoff](../reports/DEF-041-shred-audit-failure-state.md).
- The cryptographic operation did not expose the shredded secret, and the failed audit append did not corrupt the preexisting chain. No broad transactional guarantee is inferred from this SQLite injection.
