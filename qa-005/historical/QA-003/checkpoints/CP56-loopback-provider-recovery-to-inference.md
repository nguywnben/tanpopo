**Baseline:** RC5 source `3423d4f523ef0ac77469a1201b8b753d1d31c902`
**Runtime:** isolated SQLite `--role all`, synthetic fresh tenant, Chromium 156/Linux, mock provider bound only to loopback
**Status:** scoped journey completed; QA-003 remains in progress and `GATE-REL-07` BLOCKED.

## Journey

1. Reused the fresh synthetic owner and the explicitly scoped `127.0.0.1/32` Ollama connection created after CP55. No provider credential was bound. The local provider endpoint initially had no accepting listener.
2. Selected the connection's Probe action in the real Providers UI. The request returned a transport/upstream-unreachable failure; the row stayed Unverified. The failure state was captured and visually inspected in [CP56-probe-failed.png](../evidence/CP56-probe-failed.png).
3. Started a local synthetic Ollama-compatible HTTP fixture on loopback only. It returns a deterministic model-list response and a fixed synthetic chat completion; it has no Internet or real-provider dependency. Retried Probe through the UI. Tanpopo returned HTTP 200 with `valid=true`, 8 ms latency, and detected model `qa003-cp56-local`. The connection changed to Active and survived navigation/reload (API state version 9); the recovered and refreshed screens were visually inspected in [CP56-probe-recovered.png](../evidence/CP56-probe-recovered.png) and [CP56-probe-persisted-refresh.png](../evidence/CP56-probe-persisted-refresh.png). Sanitized readback is [CP56-probe-recovery-result.json](../evidence/CP56-probe-recovery-result.json).
4. Registered `qa003-cp56-local` through Models with streaming capability and synthetic context/output limits. API creation returned 201 and state DECLARED. Created a zero-rate deployment attached to the active connection; it became ACTIVE_HEALTHY, with the persisted self-hosted zero-rate marker and ON_PREM region. Visual evidence: [CP56-model-created.png](../evidence/CP56-model-created.png), [CP56-deployment-created.png](../evidence/CP56-deployment-created.png); sanitized results: [model](../evidence/CP56-model-result.json) and [deployment](../evidence/CP56-deployment-result.json).
5. Created route `qa003-cp56-route` in the UI with that deployment as its sole priority target. API returned 201; a subsequent scoped read confirmed the saved target ID, priority 1 and weight 100. See [CP56-route-created.png](../evidence/CP56-route-created.png) and [CP56-route-result.json](../evidence/CP56-route-result.json).
6. Sent a real Playground prompt through the route. The local mock returned `CP56 local mock reply`; the data-plane request returned 200, cost `$0`, and a 17 ms trace. The UI transcript and result were visually inspected in [CP56-playground-success.png](../evidence/CP56-playground-success.png); API evidence: [CP56-playground-result.json](../evidence/CP56-playground-result.json).
7. Navigated to Traces and FinOps after the request. The trace remained visible with the route, HTTP 200, exact zero cost and usage metadata. Overview request/error counters and FinOps settled/estimated/hold/unmetered totals agreed with the single zero-rate request. Visually inspected [CP56-traces-cross-screen.png](../evidence/CP56-traces-cross-screen.png), [CP56-overview-after-inference.png](../evidence/CP56-overview-after-inference.png), and [CP56-finops-after-inference.png](../evidence/CP56-finops-after-inference.png). Sanitized readbacks are [trace](../evidence/CP56-trace-cross-screen-result.json) and [cross-feature totals](../evidence/CP56-cross-feature-result.json).
8. Sent an authorized tool-call request using the same declared model/deployment, which does not advertise `tool_calling`. The gateway returned 400 `capability_not_supported`; the local fixture's recorded request count did not increase. This is expected pre-dispatch capability enforcement, not provider failure. Evidence: [CP56-capability-check-result.json](../evidence/CP56-capability-check-result.json).

## Findings and limits

- The same connection recovered from a genuine local upstream outage without recreation, and a normal inference and its cross-screen records persisted.
- This exercises one Ollama-compatible loopback provider and one zero-rate route. It does not establish external-provider availability, failure after an active deployment, retries/timeouts/cancellation, multi-target failover, billing under nonzero tariffs, or the other adapter defaults.
- **DEF-050 (Low) confirmed:** with exactly one primary target and no fallback, the route drawer said “At least one fallback target does not declare tool_calling capability.” The corresponding tool request was correctly blocked before provider dispatch, and the mock saw no request. The defect is limited to inaccurate route-validation copy; it does not weaken or bypass the capability guard. Reproduction, impact, and acceptance criteria are in the [standalone handoff](../reports/DEF-050-single-primary-target-described-as-fallback.md). Screenshot: [CP56-route-target-selected.png](../evidence/CP56-route-target-selected.png).
- One intermediate fixture returned 404 because it omitted the adapter's actual `GET /v1/models` probe contract. After correcting the test fixture, Tanpopo succeeded. That harness mismatch is not classified as product behavior.
- No external egress, external provider credential, or real spend was used. No Tanpopo implementation was modified. The temporary runtime and mock are isolated and should be stopped after evidence capture.
