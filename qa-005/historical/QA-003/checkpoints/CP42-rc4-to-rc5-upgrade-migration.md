1. Started RC4 source on isolated listener `19195` with a new SQLite DB and private synthetic master-key file. Completed first-run Setup in real Chromium, creating a synthetic owner, organization, project, and default environment. The Overview displayed zero requests, zero errors, zero spend, and no active alerts. Screenshots: [initial Setup](../evidence/CP42-rc4-setup-initial.png), [no-adapter step](../evidence/CP42-rc4-setup-no-adapters.png), [Setup review](../evidence/CP42-rc4-setup-review.png), and the loaded [Overview](../evidence/CP42-rc4-setup-overview.png).
2. Through actual Console flows, sealed a synthetic API-key credential in the write-only vault, created a HUMAN Developer scoped to the project, and issued a synthetic Provider-plane Virtual Key. The one-time Virtual Key secret and synthetic credential plaintext were not persisted in evidence. The credential UI showed only `API_KEY`, ID, and fingerprint `...093e`, plus “Plaintext cannot be read again.” Screenshots: [credential metadata](../evidence/CP42-rc4-secret-metadata.png), [member form](../evidence/CP42-rc4-member-form.png), [member row after create](../evidence/CP42-rc4-member-invite-result.png), [Virtual Key form](../evidence/CP42-rc4-key-form.png), and [key list](../evidence/CP42-rc4-key-list.png).
3. Before stopping RC4, Owner login returned HTTP 200; one organization, project, environment, Developer role binding, active key and credential metadata were readable. The hash-chain verifier returned HTTP 200, `intact=true`, 18 events. The [audit UI](../evidence/CP42-rc4-audit-before.png) displayed 17 at capture time; an additional login event was recorded in the API snapshot shortly afterward. The sanitized state is in [before/after migration evidence](../evidence/CP42-migration-result.json).
4. Stopped RC4 cleanly and preserved a private pre-migration DB snapshot. Started the exact-source RC5 QA binary against the same database path and master-key file. `/healthz` and `/readyz` both returned HTTP 200. The startup applied one migration: `schema_migrations` count 22→23 and application table count 56→57; SQLite `user_version` stayed 0. No manual schema edits were made.
5. A fresh Chromium Owner login succeeded after migration. Organization/project/environment counts remained one each; the Developer role and active Virtual Key remained; the secret credential ID, `API_KEY` kind, version 1, and fingerprint `...093e` matched. The audit chain verified intact with 25 events. Overview rendered correctly; the [migrated-member table](../evidence/CP42-rc5-migrated-member.png) showed the old member as **Pending activation**.
6. Used the post-upgrade owner action to issue a new enrollment token for that pre-existing member (HTTP 201); the token stayed only in process memory. Enrollment returned HTTP 200. A separate fresh browser session signed in as the Developer and reached Overview; owner readback showed `has_password=true`, `enrollment_pending=false`, and the Developer role. The resulting audit chain verified intact with 24 events. Visually inspected [post-upgrade member Overview](../evidence/CP42-rc5-upgraded-member-login.png).
7. Restarted RC5 with the same DB and synthetic KEK. Health/readiness again returned 200. Fresh Owner login and resource readback succeeded; organization, project, Developer membership, key, and secret metadata remained, and the audit chain was intact with 26 events. See [post-restart Overview](../evidence/CP42-rc5-after-restart-owner.png) and [sanitized result](../evidence/CP42-migration-result.json).

## Coverage and limits

- **PASS, scoped:** source-built RC4→RC5 startup migration for one populated SQLite tenant; retained Owner login, workspace, membership/role, active Virtual Key, write-only credential metadata, hash-chained audit history, and post-upgrade enrollment; a second RC5 restart retained the state.
- **UNVERIFIED:** official RC4 artifact identity; secret decryption/use after migration; RC5 data-plane use of the old Virtual Key; PostgreSQL/Valkey migration; upgrade interruption/rollback; large or legacy schema variants; browser engines beyond Chromium; and production rollout/backup recovery.
- No migration defect was confirmed in this fixture. This does not establish all RC4→RC5 upgrade safety or release readiness.
