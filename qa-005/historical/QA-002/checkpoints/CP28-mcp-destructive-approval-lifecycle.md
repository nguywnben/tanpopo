## Results

- **Synthetic destructive tool setup — PASS for the tested scope.** Registered a local Streamable HTTP fixture with the real MCP Hub UI using explicit `127.0.0.1/32`; synced and pinned `record_synthetic_action` as `destructive (mandatory HITL approval)`. The fixture only stores dummy ticket IDs and integer amounts. Issued an MCP-only Virtual Key with the one exact tool grant. A first attempted key creation accidentally retained the default PROVIDER plane; it was never used and was revoked through graceful drain before use. The replacement key was verified `allowed_planes=[MCP]`, one allowed MCP tool, and its secret was retained only under `/tmp` until test cleanup.
- **Pending request — PASS.** The MCP-only key initialized Streamable HTTP and listed the exact granted tool plus `tanpopo__check_approval_and_resume`. A call for `ticket-001 / amount 37` returned standard HTTP 200 JSON-RPC with `isError=true`, state `APPROVAL_PENDING`, one request ID, binding hash, resume tool, and one-time token. Sanitized evidence omits that token. Fixture mutation count remained zero.
- **Self-approval boundary — PASS.** The request owner saw the persisted canonical argument preview in the real Security approval queue. Attempted approval by that same owner returned HTTP 403 `self_approval_forbidden`; request remained pending and no fixture mutation occurred.
- **Independent reviewer — PASS for the tested decision path.** Added a synthetic Security Reviewer through Access & Keys. Tanpopo's member-create workflow did not provision login credentials; for this isolated QA login only, a random password hash was set using Tanpopo's existing Argon2 helper and the plaintext was kept in `/tmp` then deleted. The reviewer saw the pending request and approved it through Security → Approval Queue (HTTP 200). A separate request was later rejected through the same UI (HTTP 200); both left the expected terminal decision and queue empty.
- **Bound replay, mutation defense and exact-once — PASS.** After approval, replay with amount `3,700,000` returned HTTP 403 `parameter_hash_mismatch` with fixture count unchanged. Matching `ticket-001 / amount 37` replay through the system tool returned HTTP 200 and caused exactly one synthetic fixture mutation. Reusing the same token returned HTTP 403 `parameter_hash_mismatch` and did not cause a second mutation. After the second request was rejected, replay returned HTTP 200 JSON-RPC error `approval_invalid_state`; fixture remained at one mutation.
- **Persistent evidence — PASS.** SQLite recorded request one as `CONSUMED` (version 3), requested by the key owner's principal and decided by the separate Security Reviewer; request two is `REJECTED` (version 2). Audit events include `mcp.approval.requested`, `mcp.self_approval_blocked`, `mcp.approval_decided`, `mcp.approval.consumed`, and parameter-mismatch rows. The audit UI verified the JCS chain intact across 252 events. Both CP28 Virtual Keys were revoked after testing. Token/password/key plaintext files were removed.
- **DEF-020 independently reobserved.** After reviewer approval and rejection, the queue showed zero pending approvals but the Security navigation badge continued to show `1`. A fresh application load showed both approval and kill-switch APIs empty and removed the badge. This is within DEF-020's stale Security shell badge scope; no separate defect ID is added.
- No fixture received a real external side effect. No confirmed defect was found in this MCP approval flow beyond DEF-020's stale shell badge.
