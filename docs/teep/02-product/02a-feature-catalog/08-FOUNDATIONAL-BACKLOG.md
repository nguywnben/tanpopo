## 1. P0 Data-Integrity Highlight: PostgreSQL `KEK` Retirement `FORCE RLS` Visibility Risk (`FND-001`)

> [!CAUTION]
> **`FND-001` (`P0` Data-Integrity Risk — `[SOURCE_VERIFIED — REQUIRES INDEPENDENT REPRODUCTION]`):**
> Static inspection of [`internal/admin/http/ops_lifecycle.go`](../../../../internal/admin/http/ops_lifecycle.go) (`lines 169–208`) and [`db/migrations/postgres/0001_full_schema_rls_partitions.sql`](../../../../db/migrations/postgres/0001_full_schema_rls_partitions.sql) (`lines 1363–1367`) identified that `handleRetireMasterKEK` executes `SELECT COUNT(*) FROM org_encryption_keys WHERE kek_key_id = ?` inside `withOperatorReadTx` (`current_org_id = ''`). Because `org_encryption_keys` enables `FORCE ROW LEVEL SECURITY` scoped only to `org_id = current_setting('app.current_org_id', true)`, PostgreSQL is expected to filter out all tenant rows and return `0` even when active tenant `DEK`s remain wrapped under the retiring `KEK` — risking premature bypass of the `409 org_deks_not_rewrapped` safety check (`DEF-072`).
>
> Compounding source-verified findings in `serve.go:359` show `TANPOPO_MASTER_KEY_PREVIOUS` entries receive synthetic IDs (`"kek_prev_0"`) rather than their original AAD-bound `KEK` IDs, and `RetireKEK` scrubs `KEK` bytes only from local Control-Plane process memory rather than broadcasting cluster-wide to Data-Plane nodes.
>
> **Mandatory Pre-Production Protocol:** Before any production PostgreSQL `KEK` retirement workflow is trusted or shipped, engineering must (1) write a **non-destructive ephemeral PostgreSQL 16 integration test** independently reproducing `handleRetireMasterKEK` against populated multi-org `org_encryption_keys` rows under `FORCE RLS`, and (2) remediate the count check, `<id>=<key>` previous-key parsing, and cluster-wide `KEY_RETIRE` scrub (`FEAT-059`, `NFR-011`).
