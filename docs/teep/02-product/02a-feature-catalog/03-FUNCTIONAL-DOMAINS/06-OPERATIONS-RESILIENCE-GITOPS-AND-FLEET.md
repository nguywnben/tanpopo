## `DOM-16` — Infrastructure Operations (`5` Proposed Features)

- **Domain Overview:** Infrastructure Operations (`DOM-16`) governs how Tanpopo is deployed, observed at the cluster topology layer, isolated across network management planes, backed up, migrated across storage engines, and diagnosed under production stress. For platform architects and SREs (`PER-03`) as well as security auditors (`PER-06`), trustworthy operational primitives are the difference between a toy proxy and tier-0 production infrastructure: health endpoints must reflect true Data-Plane quorum and Valkey/OTLP degradation rather than false-green placeholders, break-glass CLI tooling must treat PostgreSQL 16 HA with complete parity alongside standalone SQLite, and single-binary or cluster operators must be able to physically isolate `/admin/v1/*` and the Web Console onto a private management interface (`--admin-listen`) away from public `/v1/*` inference traffic.
- **Existing RC9 Baseline Posture:** Frozen RC9 (`ac9ae87a`) delivers a pure-Go (`CGO_ENABLED=0`) static binary, lossless 56-table `db migrate-engine` SQLite-to-PostgreSQL 16 `FORCE RLS` promotion (`[RUNTIME_VERIFIED]`), and encrypted `.tpop.enc` SQLite backups (`[RUNTIME_VERIFIED]`). However, audit and QA-005 surfaced high-priority operational gaps: `serve.go:547` deletes `cluster_nodes` rows on shutdown while `ops_lifecycle.go:145` fabricates a healthy `primary` node when empty so `0` live Data-Plane nodes or a Valkey outage still reports `Ready / OK` (`DEF-072`, `PG-007`, `[RUNTIME_VERIFIED]` & `[SOURCE_VERIFIED]`); `loaded_kek_ids_json` is omitted from SQL `SELECT` (`[SOURCE_VERIFIED]`); `handleRetireMasterKEK` exhibits a static PostgreSQL `FORCE RLS` `0`-count visibility hazard (`FND-001`, `[SOURCE_VERIFIED — REQUIRES INDEPENDENT REPRODUCTION]`); five break-glass CLI commands hardcode `sqlite.Open` (`[SOURCE_VERIFIED]`); `doctor.go:154` probes a ghost `TANPOPO_ADMIN_LISTEN_ADDR` variable ignored by `serve.go` (`FND-019`, `[SOURCE_VERIFIED]`); and three documented diagnostic/OpenAPI Admin endpoints (`smoke-test`, `support-bundle`, `openapi.json`) return HTTP `404` (`FND-006`, `[SOURCE_VERIFIED]`).
- **Progressive Self-Hosted to Enterprise Experience:** A solo self-hoster (`PER-01`) boots one zero-dependency binary on SQLite with sensible loopback defaults, one-click browser smoke tests, encrypted local backups, and optional `--admin-listen 127.0.0.1:9090` management port separation over SSH or Tailscale/WireGuard. As the deployment matures into a multi-region enterprise (`PER-03`, `PER-06`), teams promote the exact same data model onto multi-AZ Kubernetes via the official Helm chart, enforce Data-Plane quorum health gates, run `--pg-dsn` break-glass KEK rotation and PITR envelope verification against PostgreSQL 16 HA + Valkey 8 clusters (`ARCH-011`, `ARCH-012`, `ARCH-013`), and optionally deploy `FIPS 140-3` cryptographic build artifacts without changing application code.
- **Technical Selections Deferred to `TEEP-03`:** Explicitly defers to `TEEP-03`: (1) `DEC-CAND-14` (`OQ-14`) exact dual-listener router split, Unix domain socket support, and mTLS/proxy-header trust semantics for `--admin-listen`; (2) `DEC-CAND-12` (`OQ-12`) `ARCH-OBS-01` `INSTANCE` `OPERATOR` principal separation (`org_id IS NULL` vs global lookup directory) and `ARCH-011` `SECURITY DEFINER` boundary design; (3) `DEC-CAND-16` (`OQ-16`) optional `GOFIPS140` build profile validation matrix and external PostgreSQL PITR (`pgBackRest` / CloudNativePG / RDS) envelope-verification contract; and (4) `ARCH-013` Valkey failover checkpoint reconciliation lease math.

### FEAT-095 — Cluster Topology Health, Node Tombstones, KEK Inventory, Valkey/OTLP Degradation & Quorum Alerts

- **1. Feature ID & Original `CAP` Traceability:** `FEAT-095` · `CAP` Traceability: `CAP-104` · Catalog Class: `CAT-ADMIN` (`RETAINED`) · Linked Innovations: None
- **2. Functional Domain & Subdomain:** `DOM-16` (Infrastructure Operations) -> **Cluster Topology, Quorum & Dependency Health**
- **3. Plain-Language Product Summary:** Provides truthful, real-time cluster topology and subsystem health across Control-Plane and Data-Plane nodes, retaining stopped or crashed node tombstones, showing which Master KEK IDs each node has loaded, surfacing Valkey failover/fallback or OTLP export drops, and degrading cluster status whenever live Data-Plane capacity falls below configured quorum.
  - *Practical Example:* In a 2-Control-Plane + 4-Data-Plane Kubernetes deployment (`min_dataplane_quorum = 2`), three Data-Plane pods are evicted during a node-pool drain and Valkey flips to local-memory fallback. Instead of deleting node rows and reporting `Ready / OK` as in RC9, `/admin/v1/ops/cluster-status` transitions the 3 departed nodes to `STOPPED` / `UNREACHABLE` tombstones, flips overall cluster state to `DEGRADED_QUORUM_BELOW_THRESHOLD` + `VALKEY_DEGRADED_FALLBACK`, displays a high-visibility Console Operations banner, and fires an outbox alert.
  - *Explicit Trade-Offs:* Retaining `STOPPED` and `UNREACHABLE` node tombstones requires a bounded TTL reaper (e.g., auto-pruning acknowledged tombstones older than `7d`) so ephemeral autoscaling pod churn does not accumulate unbounded rows in `cluster_nodes`.
- **4. User Problem & Business Value:** Platform SREs (`PER-03`) and security leads (`PER-06`) rely on cluster status during rolling upgrades, Vault KEK rotations, and incident triage. Eliminating false-green states prevents traffic blackholes, catches split-brain KEK env mismatches before old KEKs are retired, and exposes degraded rate-limit/budget fallback immediately.
- **5. Target Personas:** `PER-03`, `PER-06`
- **6. Existing RC9 Behavior & Limitations:** `PARTIAL_IMPLEMENTATION` with verified defects (`DEF-072`, `PG-007`, `FND-014`): (1) `cmd/tanpopo/serve.go:547` executes `DELETE FROM cluster_nodes` on graceful shutdown (`[SOURCE_VERIFIED]`), erasing historical evidence of departed Data-Plane pods (`[RUNTIME_VERIFIED]` in QA-005); (2) `internal/admin/http/ops_lifecycle.go:145` fabricates a synthetic healthy `primary` node if `cluster_nodes` is empty, reporting `Ready / OK` with `0` live Data-Plane nodes (`[SOURCE_VERIFIED]`); (3) `ops_lifecycle.go:52` omits `loaded_kek_ids_json` from `SELECT` even though heartbeats write it (`[SOURCE_VERIFIED]`); and (4) Valkey outage / in-memory fallback and OTLP ring-buffer drops are hidden in `OperationsPage` (`PG-007`, `RR-010`, `[RUNTIME_VERIFIED]`).
- **7. Proposed Complete Functional Behavior:** 1. Replace shutdown `DELETE` with explicit state transition (`ACTIVE -> DRAINING -> STOPPED`) and mark missed-heartbeat nodes (`now - last_heartbeat_ms > stale_threshold_ms`) as `UNREACHABLE` tombstones with exit/last-seen metadata.
2. Remove synthetic `primary` fabrication in split-role deployments; evaluate explicit `min_dataplane_nodes` quorum (default `1` in standalone `--role all`, configurable `>= 2` in HA) to compute `HEALTHY`, `DEGRADED`, or `CRITICAL_NO_DATAPLANE`.
3. Select and render per-node `loaded_kek_ids_json`, binary version/commit skew (`N` vs `N-1`), `config_epoch` lag, `valkey_status` (`CONNECTED`, `REPLICA_PROMOTING`, `DEGRADED_LOCAL_FALLBACK`, `DISABLED`), `valkey_hold_checkpoints` reconciliation age (`ARCH-013`), and OTLP/telemetry exporter drop counters in `/admin/v1/ops/cluster-status` and `SCR-16`.
- **8. User-Facing Subfeatures:**
  - Live Cluster Node Inventory table with `ACTIVE`, `DRAINING`, `UNREACHABLE`, and `STOPPED` lifecycle states, `config_epoch` sync lag, and explicit tombstone acknowledge/prune controls.
  - Per-node Vault `loaded_kek_ids` matrix highlighting KEK skew before `Retire KEK` is permitted (`FND-001` companion safeguard).
  - Subsystem Health Strip & Banner for Valkey cluster state (`PG-007`), PostgreSQL/SQLite pool saturation, and OTLP ring-buffer drop counters.
  - Configurable Data-Plane minimum quorum policy (`min_dataplane_nodes`) driving readiness summaries, Console alerts, and Prometheus gauges.
- **9. End-to-End Lifecycle:** Node boot registers `(node_id, role, version, listen_addrs, loaded_kek_ids_json, config_epoch)` -> periodic heartbeat updates latency/epoch/dependency counters -> graceful `SIGTERM` marks `DRAINING` then `STOPPED` (or crash triggers `UNREACHABLE` after missed lease) -> operator inspects/acknowledges tombstone or background TTL reaps entries after retention window (`default 7d`).
- **10. Primary & Alternative User Journeys:** **Primary (HA Fleet Check):** SRE opens `Operations -> Cluster & Health`, verifies all 4 DP pods are `ACTIVE` on the latest `config_epoch` and all carry `kek_2026_q4` before retiring `kek_2026_q3`.
**Alternative (Single-Node Self-Hosted):** Solo user in `--role all` SQLite mode sees a concise single-node `Healthy (Standalone SQLite · Valkey Not Configured)` summary without noisy multi-node quorum warnings.
- **11. Administrative & Permission Boundaries:** Full node topology, IP/hostname metadata, and KEK IDs require `INSTANCE` `OPERATOR` (`SCR-16`). `ORG_OWNER` principals see only a sanitized platform service-health indicator (no cross-tenant infrastructure hostnames or KEK IDs).
- **12. Automation Opportunities:** Prometheus bounded gauges (`tanpopo_cluster_dataplane_nodes_active`, `tanpopo_valkey_degraded_fallback`, `tanpopo_node_config_epoch_lag`) and automatic `cluster.quorum_degraded` / `cluster.valkey_fallback` notification events (`DOM-19`).
- **13. Enterprise-Specific Requirements (`ESSENTIAL_SELF_HOSTED_AND_ENTERPRISE`):** Supports rolling `N-1 -> N` Kubernetes node-pool replacements without false alarms during `DRAINING`, scales `O(N_nodes)` cleanly independent of `N_orgs` (`ARCH-011`), and pairs with `ARCH-013` (`COND-PO-03`) Valkey checkpoint reconciliation metrics.
- **14. Core vs Extension Placement Candidate:** `CORE_CONTROL_PLANE` — Node heartbeats, KEK key-ID inventory, Valkey state, OTLP buffer saturation, and Data-Plane quorum evaluation are intrinsic kernel liveness/readiness primitives that cannot be delegated to optional plugins.
- **15. Console, CLI, API & GitOps Touchpoints:**
  - *Web Console:* `OperationsPage` (`SCR-16`) Cluster & Dependency Health tab with node tombstones, KEK matrix, and Valkey/OTLP warning banners.
  - *CLI:* `tanpopo ops cluster-status` and `tanpopo ops nodes prune --stopped-before 24h` (table/json/yaml).
  - *Admin / Data-Plane API:* `GET /admin/v1/ops/cluster-status`, `DELETE /admin/v1/ops/cluster-nodes/{nodeId}` (tombstone dismissal).
  - *GitOps / Terraform / Packs:* `clusterPolicy.minDataplaneQuorum` and `staleNodeTtlSeconds` declarative server/helm settings.
- **16. Dependencies & Cross-Domain Relationships:** `Resolves `FND-014` (`DEF-072` topology defects, `PG-007`, `RR-010`).`, `Pairs with `FEAT-059` / `FND-001` (safe multi-node Vault `KEK` rotation/retirement) and `ARCH-013` (Valkey failover reconciliation).`, `Feeds `FEAT-112` & `FEAT-114` operational degradation notifications.` · Related Decisions: `DEC-CAND-12`
- **17. Failure & Recovery Behavior:** If the database itself is unreachable, node-local `/healthz` and `/readyz` report local snapshot/DB readiness honestly (`503` on readiness check if ServingReady fails) without panicking; when Valkey recovers from fallback, `ARCH-013` reconciles `valkey_hold_checkpoints` before clearing the `DEGRADED_LOCAL_FALLBACK` banner.
- **18. Security, Privacy & Financial Implications:** Exposes key *identifiers* (`kek_id`) only — never key material. Honest Valkey fallback visibility informs FinOps controllers (`PER-07`) when distributed budget leases temporarily fall back to conservative DB/per-pod enforcement.
- **19. Preliminary Measurable Acceptance Criteria:**
  - Stopping all Data-Plane processes in a split CP/DP cluster transitions departed rows to `STOPPED`/`UNREACHABLE` and flips `/admin/v1/ops/cluster-status` from `HEALTHY` to `CRITICAL_NO_DATAPLANE` (`0` fabricated `primary` rows).
  - `GET /admin/v1/ops/cluster-status` returns non-empty `loaded_kek_ids` matching each live node's Vault keyring and blocks `Retire KEK` with actionable node IDs if skew exists.
  - Killing Valkey under load surfaces `valkey_status = DEGRADED_LOCAL_FALLBACK` in both API and `OperationsPage` within `<= 1` heartbeat interval (`[HYPOTHESIS]`), resolving `PG-007`.
- **20. Relevant Evidence & Research Confidence:** `HIGH` — Grounded in `[RUNTIME_VERIFIED]` QA-005 `DEF-072`/`PG-007` reproductions and `[SOURCE_VERIFIED]` code inspection of `cmd/tanpopo/serve.go:547` and `internal/admin/http/ops_lifecycle.go:52,145`.
- **21. Proposal Classification:** `IMPROVE` (`RETAINED`)
- **22. Candidate Release Priority, Rationale & Scenario Affinity:** **`P0-Foundational`** — P0-Foundational because false-green health reporting (`DEF-072`, `PG-007`) masks complete Data-Plane outages, silent Valkey single-node fallbacks, and partial KEK rotation states in production HA clusters. *(Scenario Mapping: `SCEN-A`: `v1.0.0` · `SCEN-B`: `v1.0.0` · `SCEN-C`: `v1.0.0` · `SCEN-D`: `v1.0.0 (Core)`)*

### FEAT-096 — Dual-Engine (SQLite & PostgreSQL) Operational Break-Glass CLI & Verified Backup/PITR Workflows

- **1. Feature ID & Original `CAP` Traceability:** `FEAT-096` · `CAP` Traceability: `CAP-105` · Catalog Class: `CAT-ADMIN` (`RETAINED`) · Linked Innovations: None
- **2. Functional Domain & Subdomain:** `DOM-16` (Infrastructure Operations) -> **Break-Glass Operations, Backup & Disaster Recovery**
- **3. Plain-Language Product Summary:** Brings 100% dual-engine (`SQLite` and `PostgreSQL 16+`) parity to every operational break-glass CLI command — including Vault KEK rotation, upgrade preflight, emergency owner password/MFA reset, tenant crypto-shredding, and air-gap bundle import — while pairing encrypted `.tpop.enc` SQLite snapshots with native PostgreSQL PITR / `pg_dump` cryptographic envelope and audit-chain verification (`tanpopo backup verify-pg`).
  - *Practical Example:* During a quarterly security drill on an AWS RDS PostgreSQL 16 cluster, an SRE runs `tanpopo vault rotate-kek --pg-dsn-env TANPOPO_PG_DSN` followed by `tanpopo backup verify-pg --pg-dsn-env TANPOPO_PG_DSN` against a restored PITR staging clone, confirming `100%` of tenant DEK envelopes, secret credentials, and JCS audit chains unwrap and verify cleanly under the new KEK without touching SQLite.
  - *Explicit Trade-Offs:* Rather than reinventing a custom logical backup format for multi-hundred-GB PostgreSQL clusters (`OQ-16`), Tanpopo delegates physical PG snapshots/WAL archiving to battle-tested Postgres tools (`pgBackRest`, CloudNativePG, RDS) and focuses `tanpopo backup verify-pg` on cryptographic Vault/JCS consistency — trading a single proprietary archive format across engines for enterprise DBA reliability at terabyte scale (`[DESIGN_PROPOSAL]`).
- **4. User Problem & Business Value:** Eliminates the operational cliff discovered when graduating from standalone SQLite (`PER-01`) to PostgreSQL HA (`PER-03`, `PER-06`), ensuring disaster recovery runbooks, quarterly KEK rotations, and emergency lockout recovery actually execute on production databases (`RR-015`).
- **5. Target Personas:** `PER-03`, `PER-06`, `PER-01`
- **6. Existing RC9 Behavior & Limitations:** `PARTIAL_IMPLEMENTATION` (`[RUNTIME_VERIFIED]` on SQLite; `[SOURCE_VERIFIED]` broken on PostgreSQL): encrypted `.tpop.enc` SQLite backup/restore and `db migrate-engine` pass on SQLite -> PG16 (`[RUNTIME_VERIFIED]`), **but** `vault rotate-kek`, `backup create`, `upgrade preflight`, `tenant shred`, `admin reset-local-owner`, and `bundle import --db` hardcode `sqlite.Open(...)` in `internal/cli/ops/commands.go` and `internal/cli/bundle/import.go` (`[SOURCE_VERIFIED]`, `RR-015`, `DEF-072`), and `DEF-086` revealed missing CI width-parity checks (`ARCH-012`).
- **7. Proposed Complete Functional Behavior:** 1. Unified Storage Factory in CLI: accept `--storage-engine={sqlite|postgres}`, `--db` (SQLite), and `--pg-dsn` / `--pg-dsn-file` / `TANPOPO_PG_DSN` across `vault rotate-kek`, `upgrade preflight`, `tenant shred`, `admin reset-local-owner`, `admin verify-state`, and `bundle import`.
2. PostgreSQL Backup & PITR Verifier (`tanpopo backup verify-pg`): connects to a restored PG clone under `CheckNonPrivilegedRole`, verifies schema version parity (`ARCH-012`), runs RLS-safe `VerifyAllDEKEnvelopes`, `VerifyAllSecretEnvelopes`, and `VerifyAllAuditChains` (including `audit_partition_seals` `ARCH-010`), and outputs a JCS-signed DR verification receipt.
3. Retains one-command `tanpopo backup create | verify | restore` `.tpop.enc` AEAD-encrypted backups for Mode A SQLite.
- **8. User-Facing Subfeatures:**
  - Dual-engine CLI flags (`--pg-dsn-file`, `TANPOPO_PG_DSN`, `--db`) across all 6 break-glass ops and bundle subcommands.
  - `tanpopo backup verify-pg` post-restore cryptographic envelope, DEK/KEK lineage, and JCS audit-chain verifier with JSON attestation output.
  - `tanpopo upgrade preflight` N-1/N rolling schema-skew, pending-migration, and extension-ABI compatibility checker (`ARCH-012`).
  - Guided Disaster Recovery & Engine-Promotion Runbook panel in `OperationsPage` (`SCR-16`) generating copy-ready CLI commands for the active storage engine.
- **9. End-to-End Lifecycle:** Pre-maintenance `tanpopo upgrade preflight` -> physical snapshot (`.tpop.enc` for SQLite or `pgBackRest`/RDS snapshot for PG) -> maintenance mutation (`db migrate`, `vault rotate-kek`, `tenant shred`) under PostgreSQL advisory lock -> post-restore `tanpopo backup verify-pg` / `backup verify` attestation.
- **10. Primary & Alternative User Journeys:** **Primary (PostgreSQL HA Break-Glass):** IdP outage locks out SSO admins; SRE execs into maintenance pod and runs `tanpopo admin reset-local-owner --pg-dsn-file /run/secrets/pg_dsn` to restore break-glass access safely.
**Alternative (SQLite Homelab Backup):** Solo user runs `tanpopo backup create --out /backups/daily.tpop.enc` via cron with zero Postgres tooling required.
- **11. Administrative & Permission Boundaries:** CLI break-glass operations require direct OS/secret access to the database DSN and Vault Master KEK/KMS role, enforce `CheckNonPrivilegedRole` (refusing `SUPERUSER`/`BYPASSRLS` runtime roles), and append immutable `SYSTEM` audit chain entries (`actor_type = CLI_BREAK_GLASS`).
- **12. Automation Opportunities:** Scheduled CI/CD DR verification job restoring nightly RDS/CNPG snapshots into ephemeral containers and asserting exit code `0` from `tanpopo backup verify-pg --json`.
- **13. Enterprise-Specific Requirements (`ESSENTIAL_SELF_HOSTED_AND_ENTERPRISE`):** Zero raw DSNs or KEKs on process `argv` (`--pg-dsn-file` / env only), PostgreSQL advisory lock coordination to prevent concurrent `rotate-kek` races across pods, and `ARCH-012` dual-engine DDL width parity enforcement.
- **14. Core vs Extension Placement Candidate:** `CORE_CONTROL_PLANE` — Offline/break-glass Vault envelope verification, KEK rotation, local-owner recovery, and migration preflight must ship inside the single `tanpopo` binary for zero-dependency emergency execution.
- **15. Console, CLI, API & GitOps Touchpoints:**
  - *Web Console:* `OperationsPage` (`SCR-16`) Backup, Engine Status & Upgrade Preflight status card (read-only guidance + preflight check).
  - *CLI:* `tanpopo vault rotate-kek`, `upgrade preflight`, `tenant shred`, `admin reset-local-owner`, `backup create|verify|restore|verify-pg`.
  - *Admin / Data-Plane API:* `GET /admin/v1/ops/preflight` (read-only schema & N-1 skew readiness report for `OPERATOR`).
  - *GitOps / Terraform / Packs:* Pre-sync Kubernetes `Job` / ArgoCD PreSync hook running `tanpopo upgrade preflight` before rolling deployments.
- **16. Dependencies & Cross-Domain Relationships:** `Resolves `RR-015`, `DEF-072` CLI SQLite cliff, and pairs with `FND-001` (`handleRetireMasterKEK` RLS fix) & `FND-007` (`DEF-041` erasure).`, `Relies on `ARCH-011` (`ARCH-OBS-01` RLS-safe cross-org helpers) and `ARCH-012` (dual-engine schema parity guard).`, `Shares dual-engine storage factory with `FEAT-111` (`.tpbundle` PG import).` · Related Decisions: `DEC-CAND-16`
- **17. Failure & Recovery Behavior:** All multi-org break-glass mutations use resumable idempotent checkpoints under advisory locks; if interrupted mid-run, re-running `vault rotate-kek` or `tenant shred` safely resumes remaining unwrapped/unshredded rows without corrupting dual-KEK readability.
- **18. Security, Privacy & Financial Implications:** Prevents cold-backup DEK resurrection hazards when combined with external KMS (`FEAT-059`) and ensures `usage_settlements` and `budget_ledgers` integrity is cryptographically verified after any PITR recovery.
- **19. Preliminary Measurable Acceptance Criteria:**
  - All 6 break-glass/bundle CLI commands (`vault rotate-kek`, `upgrade preflight`, `tenant shred`, `admin reset-local-owner`, `admin verify-state`, `bundle import`) pass automated E2E suites against both SQLite and PostgreSQL 16 (`FORCE RLS` enabled).
  - `tanpopo backup verify-pg` detects a deliberately tampered `secret_credentials` ciphertext or broken `audit_events` hash in a staging PG16 database and exits non-zero with exact diagnostic codes.
  - Zero CLI command accepts plaintext passwords, KEKs, or DSN credentials as bare positional flags visible in `/proc/<pid>/cmdline`.
- **20. Relevant Evidence & Research Confidence:** `HIGH` — `[SOURCE_VERIFIED]` inspection of `internal/cli/ops/commands.go` and `internal/cli/bundle/import.go` confirming `sqlite.Open` hardcoding (`TEEP-01-DOC-04`, `RR-015`).
- **21. Proposal Classification:** `IMPROVE` (`RETAINED`)
- **22. Candidate Release Priority, Rationale & Scenario Affinity:** **`P0-Foundational`** — P0-Foundational because production Mode B/C deployments run PostgreSQL 16 HA, yet five break-glass CLI commands in RC9 hardcode `sqlite.Open`, leaving PostgreSQL operators stranded during KEK rotation, owner lockout, or tenant erasure. *(Scenario Mapping: `SCEN-A`: `v1.0.0` · `SCEN-B`: `v1.0.0` · `SCEN-C`: `v1.0.0` · `SCEN-D`: `v1.0.0 (Core)`)*

### FEAT-097 — Production Kubernetes Helm Chart, Multi-Arch Container Artifacts & Optional FIPS 140-3 Build Profile

- **1. Feature ID & Original `CAP` Traceability:** `FEAT-097` · `CAP` Traceability: `CAP-107` · Catalog Class: `CAT-ADMIN` (`RETAINED`) · Linked Innovations: None
- **2. Functional Domain & Subdomain:** `DOM-16` (Infrastructure Operations) -> **Cloud-Native Packaging, Containers & Cryptographic Build Profiles**
- **3. Plain-Language Product Summary:** Delivers signed, multi-architecture (`linux/amd64`, `linux/arm64`) rootless distroless OCI images, a production-hardened Kubernetes Helm chart supporting both unified and split Control-Plane / Data-Plane topologies with zero-drop SSE drain hooks, and an optional `CGO_ENABLED=0` `FIPS 140-3` build profile (`tanpopo-fips`) — while keeping standalone non-Kubernetes binaries and Docker Compose first-class.
  - *Practical Example:* A healthcare platform team installs `oci://ghcr.io/tanpopo/charts/tanpopo` onto EKS ARM64 Graviton nodes using the `tanpopo-fips` image tag, automatically provisioning 2 Control-Plane replicas (bound to an internal ALB via `--admin-listen`), an HPA-scaled 6-pod Data-Plane pool with `preStop` SSE drain hooks, `PodDisruptionBudget`s, strict `NetworkPolicy` manifests, and a `ServiceMonitor` for Prometheus.
  - *Explicit Trade-Offs:* Maintaining an optional `GOFIPS140` cryptographic build profile (`DEC-CAND-16`) restricts cipher suites to NIST-approved primitives (e.g., disallowing ChaCha20-Poly1305 or pure-Ed25519 where disallowed by strict FIPS policy unless hybrid/approved modes are used) and adds a second artifact matrix in CI.
- **4. User Problem & Business Value:** Saves enterprise SREs weeks of hand-crafting Kubernetes manifests, prevents rolling-upgrade stream drops (`0.17%` drop rate observed in RC9 `RR-020`), unlocks ARM64 cloud cost savings (`RR-005`), and removes federal / financial procurement blockers around container hardening and cryptographic module posture.
- **5. Target Personas:** `PER-03`, `PER-06`, `PER-01`
- **6. Existing RC9 Behavior & Limitations:** `PARTIAL_IMPLEMENTATION`: RC9 compiles cleanly with `CGO_ENABLED=0` and includes baseline Docker/Compose assets, but lacks a full production Helm chart with split CP/DP `Deployment`s, `NetworkPolicy`, `PodDisruptionBudget`, `ServiceMonitor`, and `preStop` drain orchestration (`[SOURCE_VERIFIED]`); multi-host Kubernetes HA and native `linux/arm64`, `darwin/arm64`, and `windows/amd64` runtime test matrices remain unexecuted (`RR-005`, `RR-023`, `RR-029`, `[SOURCE_VERIFIED]`); and no `FIPS 140-3` build profile is packaged (`[SOURCE_VERIFIED]`).
- **7. Proposed Complete Functional Behavior:** 1. ### FEAT-098 — Dedicated Admin Plane Network Listener & Management Port Isolation (--admin-listen)

- **1. Feature ID & Original `CAP` Traceability:** `FEAT-098` · `CAP` Traceability: `NEW-TEEP-02A` (Expanded Underrepresented Capability) · Catalog Class: `CAT-ADMIN` (`ADDED_IN_TEEP_02A`) · Linked Innovations: None

- **3. Plain-Language Product Summary:** Allows operators in either single-binary (`--role all`) or multi-node cluster mode to bind the Admin API (`/admin/v1/*`), embedded Web Console UI, and optional diagnostics/metrics onto a dedicated private management address, port, VLAN, or WireGuard/Tailscale interface (`--admin-listen` / `TANPOPO_ADMIN_LISTEN_ADDR`), while keeping the Data Plane (`/v1/*`, `/native/*`, `/mcp`, `/a2a`) on the workload listener (`--listen`) with zero admin routes mounted on the public socket.
  - *Practical Example:* A self-hoster (`PER-01`) on a cloud VPS runs `tanpopo serve --listen 0.0.0.0:8080 --admin-listen 100.64.0.12:9090` (Tailscale/WireGuard IP) or `127.0.0.1:9090` (SSH tunnel), and an enterprise Kubernetes team (`PER-03`) binds `--listen 0.0.0.0:8080` to the app-mesh `Service` while binding `--admin-listen 0.0.0.0:9090` strictly to an internal corp-VPN Ingress and `NetworkPolicy`. - **4. - **3.
