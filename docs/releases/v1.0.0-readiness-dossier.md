## 3. Canary Progressive Rollout Policy & Live `< 60s` `DR-04` Rollback Verification

### 3.1. Traffic Shift & Automatic Rollback Thresholds

Production Kubernetes (`deploy/helm/tanpopo/values.yaml`) and reverse-proxy upgrades follow a monotonic progressive rollout coupled strictly to `Expand-Only` DB migrations ([`backups-recovery.md`](../operations/backups-recovery.md) §`DR-04`):

| Stage | Canary Weight | Minimum Soak | Automatic Rollback Triggers (`ALT-*` / `SLO-*` Immediate `-> 0%`) |
|---|---|---|---|
| **Pre-flight** | `0%` (`--dry-run`) | — | `tanpopo upgrade preflight` exits `22` (`BLOCKED_INCOMPATIBLE`) or `/readyz != 200` within `< 3.0s` |
| **Stage 1** | `5%` | `15 min` | `ALT-GATEWAY-BURN`: Internal `5xx` (excl. `upstream_*`) `> 0.05%` over `5 min` or `> 2%` monthly budget burn in `1h` |
| **Stage 2** | `25%` | `30 min` | `ALT-LATENCY-SLO`: Proxy overhead `p95 > 10 ms` (`> 2 ms` Tier-1 target) for `5 min`, OR `ALT-REVOCATION-LAG`: `config_snapshot_age_seconds > 5s` for `> 30s` |
| **Stage 3** | `50%` | `30 min` | `ALT-PLUGIN-TRAP`: `> 20` Wasm faults/`60s`, OR any `ALT-AUDIT-TAMPER` / DB schema compatibility failure |
| **Stage 4** | `100%` | Release Complete | Retain `N-1` `Expand-Only` column compatibility for `>= 1` minor release cycle so instant `DR-04` downgrade requires zero DB restore |

### 3.2. Empirical `< 60s` Live Canary Rollback Drill (`scripts/release/canary_rollback_drill_test.go`)

Executed via `go test -v -race -count=1 ./scripts/release -run TestGATEREL02AndDR04_LiveCanaryRolloutAndSub60sRollback`:
- **Honest Test Harness Scope:** Exercises two real compiled `tanpopo` binaries (`CGO_ENABLED=0` `baseline` and `canary`) fronted by an in-process weighted Go reverse-proxy test harness on loopback (simulating ingress weight shift & `SIGKILL`/`SIGINT` pod drain rather than a full Kubernetes `helm rollback`).
- **True `N-1` `Expand-Only` Schema Proof:** After owner bootstrap and Virtual Key creation on `baseline`, `baseDBFile` receives an additive forward column (`ALTER TABLE organizations ADD COLUMN canary_expand_only_note ...`), is cloned via parameterized `VACUUM INTO ?` for `canary`, and **both `baseline` (`N-1` binary role) and `canary` restart cleanly on the expanded schema**, serving `/readyz=200` and `/v1/models=200`.
- **Progressive Stages & Continuous `baseline`-Backed SSE:** `4` long-lived SSE streams backed continuously by `baseline` `/v1/models` ticks establish cleanly behind a readiness barrier before Stage 1, remaining uninterrupted across `5%` (`5/100`), `25%` (`25/100`), and `50%` (`50/100`) canary weight shifts (`0` errors).
- **Fault Injection & `DR-04` Rollback Timing:** After injecting `20` simulated canary `5xx` errors (`ALT-GATEWAY-BURN`), the controller flips canary weight atomically to `0%`, stops the `canary` binary (`SIGINT`), verifies `50/50` (`100%`) `200 OK` responses immediately on `baseline` against the `Expand-Only` DB, and asserts **`0` premature SSE drops** across the entire rollout/rollback in **`24.76 ms` (`-race`, `< 60s` SLA; `N-1` `baseNode` restarted on Expand-Only DB; `canary_5xx=20`, `post_rollback=50/50`, `sse_dropped=0`)** (strictly `< 60s` SLA).
